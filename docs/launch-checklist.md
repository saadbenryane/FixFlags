# FixFlags launch checklist

This is the operational release checklist. It does not define product strategy, packaging, or customer language. Those decisions live in [the product masterplan](product-masterplan.md), [PRODUCT.md](../PRODUCT.md), and [voice and copy](voice-and-copy.md).

Current commercial truth:

- Free: one website, verified weekly.
- Pro: $49 per website per month, verified every day.
- Studio: the same product for several websites, quoted and billed per website.
- Paid checkout is closed. Public paid calls to action join the waitlist.
- Do not enable `STRIPE_PAID_OPEN` or `NEXT_PUBLIC_PAID_OPEN` until blocker B5 in the product masterplan is complete.

## Release boundary

A release is ready only when all Blockers in the product masterplan are checked and the receipt-backed release sequence passes on the exact candidate commit. A green local build is necessary but is not a production launch decision.

Run from a clean candidate revision:

```bash
npm run doctor
npm run verify
npm run verify:release
```

`verify:release` owns the authoritative stage order:

1. Foundation: clean install, disposable database migrations, full verification, image build, web and worker topology, and one real completed scan.
2. Fixture binding: exact-revision remote release environment plus the private disposable fixture manifest.
3. Credentialed core: signup, claim, Site return, Flag, Fix, Verify, Watch, notification return, support, and access boundaries.
4. Billing open and billing closed: test-mode checkout, webhook transitions, portal, revocation, and waitlist behavior in both switch states.
5. External providers: only integrations that are exposed to customers.
6. Deployed proof: health and readiness on the exact candidate SHA, followed by final receipt validation.

Required inputs are generated by the current release scripts. Do not copy an older environment list from a session note. The minimum foundation inputs are:

- `RELEASE_FRESH_DATABASE_URL` pointing to a disposable database whose name contains `release` or `test`
- `RELEASE_ALLOW_DATABASE_RESET=true`
- `RELEASE_CONTAINER_ENV_FILE`

Remote and credentialed stages additionally require:

- `RELEASE_E2E_TARGET=remote`
- `RELEASE_ENV_URL` serving the exact candidate revision
- `RELEASE_FIXTURE_MANIFEST` containing disposable, non-production identities
- the provider and sandbox credentials demanded by `scripts/release-preflight.mjs`

Release stages fail closed when evidence or credentials are missing. Never replace a required probe with a skip.

## Paid-launch gate

Before accepting money:

- Measure the per-Site cost baseline and record the decision against B5.
- Create matching Stripe test and live prices for the canonical $49 Pro per-website offer. Studio remains quoted until its per-website contract is explicit.
- Verify price IDs, quantities, entitlements, checkout copy, invoices, webhook transitions, failed-payment recovery, cancellation, and the billing UI agree.
- Complete the test-mode paid and closed-switch release stages.
- Keep server and client paid switches equal.
- Create and verify a live webhook before the first real charge.
- Perform one controlled real charge, verify entitlement and invoice state, then refund if appropriate.

Detailed Stripe environment setup is in [stripe-setup.md](stripe-setup.md). Historical prices, founder discounts, Product Review allowances, and batch-launch plans are not current packaging.

## Production promotion

1. Push the verified candidate to `origin/main` only when the release owner intends to deploy it.
2. Wait for both Railway web and worker services to report success for the exact commit.
3. Confirm `/api/health/ready` reports database, Redis, migrations, worker, storage, browser, AI, and email readiness without a required subsystem missing.
4. Confirm `/api/health` reports the exact candidate commit.
5. Run the deployed stage and final receipt. Verify canonical image URLs, public route boundaries, and the critical customer journeys.
6. Record the receipt and journey evidence in the active session record, then update the product masterplan.

## Rollback

If readiness, the worker, a critical journey, or billing fails:

1. Close paid checkout immediately if it was opened.
2. Roll web and worker back to the last jointly verified revision.
3. Confirm both services and `/api/health` report that revision.
4. Preserve failed release receipts and logs. Do not overwrite them with a manual PASS.
5. Re-run the affected release stage before promoting another candidate.
