## Current scope and completion standard

The supported website product includes URL entry, persistent Site claiming, all eight coverage areas, individual and grouped Flag repair, category and page depth, comparable verification, recurrence, automatic HTTP uptime, scheduled analysis, notifications, authorized account checks, account settings and acknowledged Site removal. Preserve existing commercial policy, subscriptions, credits, saved connections and historical reports. Do not open paid enrollment, public machine-client discovery or another gated integration merely to complete a demonstration.

Completion requires the full customer loop, trustworthy shared facts, meaningful evidence for every locally testable advertised item, coherent implementation, a minimal usable interface and representative integrated application/database/queue/worker behavior. A test total, registered evaluator, completed Audit, copied task or healthy endpoint cannot establish that standard alone.

### Outcome and design

Routine uptime and native checks keep their required cadence and fresh evidence without generative AI. Established check recipes produce useful instructions immediately. Semantic models handle bounded judgments; generative models contribute only missing contextual explanation. A provider outage cannot erase observations, stop independent checks, remove a known failure, fabricate an assessment or produce a false recovery. Preserve customer credits, commercial policy, the current interface and all advertised responsibilities.

The logical path is:

```text
Site authority and scheduled intent
  -> fresh required observations
  -> deterministic conclusions and durable incident identity
  -> one source-bound repair definition
  -> compatible interpretation reuse or bounded semantic evaluation when needed
  -> new contextual prose only when it adds required value
  -> independent comparable verification and continuing monitoring
```

This describes responsibility, not one blocking serial pipeline. Independent collections publish independently. Existing PostgreSQL task/evidence ownership, BullMQ delivery, provider usage custody and repair definitions remain the foundation. Model choice belongs behind those contracts, with capability-specific adapters. Avoid a new generic agent platform, a second incident store, a second scheduler or a separate AI dashboard.

## Research applied to the plan

The November 5 refresh rechecked primary guidance for monitoring, delivery, usability, accessibility and performance. The recommendations below are applications of those sources to the inspected FixFlags implementation, not evidence that this candidate meets their requirements.

The November 7 research adds four concrete acceptance decisions:

- Evaluate detection confirmation and recovery separately. On the existing Uptime generation, distinguish first failure, confirmed outage, verified return and a missing probe. Check a flapping target and verify that HTTP recovery cannot resolve a rendered checkout Flag. [Better Stack confirmation and recovery](https://betterstack.com/docs/uptime/confirmation-and-recovery-period/), [Checkly retry strategies](https://feedback.checklyhq.com/changelog/announcing-smart-retries).
- Keep synthetic measurements, URL-level field data and origin-level field data visibly attributed. Where a URL has insufficient CrUX data, show the scope of any separately available origin result and preserve the URL-level unknown. Compare repairs in the same device and measurement context. [DebugBear synthetic monitoring](https://www.debugbear.com/docs/synthetic-website-monitoring), [Chrome UX Report methodology](https://developer.chrome.com/docs/crux/methodology/).
- Start Flag detail with the most relevant recorded observation and its next action. Put earlier occurrences and supporting measurements in the existing disclosure and Timeline. Verify whether an owner can explain the evidence and distinguish a previous recovery from a recurrence. [Sentry Issue Details](https://docs.sentry.io/product/issues/issue-details/?promo_name=hp-banner).
- Ask owners to perform believable tasks without naming the interface controls. Observe what they understand and where they hesitate. On the same build, validate accessible authentication, focus through sticky controls and overlays, and announcements after check and repair actions. Keep the existing contrast exception explicit. [GOV.UK moderated usability testing](https://www.gov.uk/service-manual/user-research/using-moderated-usability-testing), [WCAG 2.2](https://www.w3.org/TR/WCAG22/).

Operational alerts should reflect meaningful symptoms and support diagnosis, with external observations distinguished from internal health. This supports the existing separation between uptime, functional checks and service readiness. [Google SRE](https://sre.google/sre-book/monitoring-distributed-systems/).

Retries need stable operation identity and intent; a timeout alone cannot prove that a remote effect did not happen. Keep the durable effect and reconciliation owners already built. [AWS Builders Library](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/).

Queue locks can be lost when workers stop renewing them. Preserve explicit ledger recovery and resource bounds rather than equating a broker job state with completed product work. [BullMQ stalled jobs](https://docs.bullmq.io/guide/jobs/stalled).

Important status changes must be programmatically available without forcing focus, and detected input errors need identifying text. Apply these requirements to real action states and forms, not just static rendering. [W3C status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html), [W3C error identification](https://www.w3.org/WAI/WCAG22/Understanding/error-identification).

Focused controls must remain at least partially visible through authored sticky content and overlays. Test the actual viewport and keyboard position, rather than inferring a failure from a tall page image. Preserve the stronger existing focus treatment where available. [W3C focus not obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html).

The performance targets above follow Google's current LCP, INP and CLS guidance. Field acceptance uses the 75th percentile with mobile and desktop considered separately. A fast local interaction or a Lighthouse result cannot establish that field result. [Google Web Vitals](https://web.dev/articles/vitals).

Resend deduplicates supported idempotent sends within a 24-hour window and requires the original request body for webhook verification. Preserve durable delivery identity and bounded reconciliation beyond the provider's retry window; distinguish provider acceptance, delivery and human reading. [Resend idempotency keys](https://resend.com/docs/dashboard/emails/idempotency-keys), [Resend webhook verification](https://resend.com/docs/webhooks/verify-webhooks-requests).

Operational alert acceptance should consider significance, precision, detection and reset time. Apply that reasoning to FixFlags' existing missed-obligation signals, without copying a large request-rate alerting framework into a low-volume product. [Google SRE alerting guidance](https://sre.google/workbook/alerting-on-slos/).

Resend defines `email.sent` as a successful API request and `email.delivered` as delivery to the recipient's mail server. Neither alone establishes that the person received a usable task. The repair/email acceptance therefore follows the actual message and source link through the intended recipient's next action. [Resend event types](https://resend.com/docs/webhooks/event-types).

Authentication accessibility includes mechanisms that reduce memory/transcription burden, such as password managers and paste. Evaluate these in the actual claim and return journey. W3C also distinguishes conformance testing, which needs automated and human evaluation, from usability. Preserve the documented contrast exception and identify the evidence that is still absent. [W3C accessible authentication](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html), [W3C conformance guidance](https://www.w3.org/WAI/WCAG22/Understanding/conformance).

Task-based usability work observes whether people can achieve specific results. Apply that method to discovery, repair, verification and leaving monitoring active, with task outcomes set in advance. Agent walkthroughs prepare and improve those journeys but cannot be relabeled participant research. [GOV.UK usability testing](https://www.gov.uk/service-manual/user-research/using-moderated-usability-testing).

Prompt-injection defenses need limits outside model instructions as well as separation of untrusted content. Preserve the existing native origin, permission, scope and publication boundaries when reducing prompts, reusing interpretations or testing other models. Add adversarial evidence to the same task evaluation instead of treating structured output as proof of trustworthy judgment. [OWASP prompt injection prevention](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html).
